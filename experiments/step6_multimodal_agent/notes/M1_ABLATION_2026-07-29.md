# M1 architecture ablation

The campaign compares the independently switchable M1 blocks on the same
cue-and-recall environment. It reports visible-cue reward (representation and
policy control), hidden-cue reward (memory), parameter count and CPU forward
latency. These are smoke metrics, not general multimodal claims.

Run:

```bash
PYTHONPATH=src:. .venv/bin/python experiments/step6_multimodal_agent/scripts/run_m1_ablation.py --episodes 100 --output artifacts/m1_ablation.json
```

## Smoke result (seed 0, 100 episodes)

| Variant | Params | Visible reward | Hidden reward | Forward ms |
|---|---:|---:|---:|---:|
| baseline | 37,830 | 0.95 | 0.40 | 0.118 |
| Engram | 88,147 | 0.45 | 0.45 | 1.589 |
| JEPA | 62,726 | 0.50 | 0.45 | 0.147 |
| Loop | 71,430 | 0.35 | 0.55 | 0.787 |
| spectral | 71,623 | 0.55 | 0.45 | 1.810 |
| Engram + JEPA + Loop | 146,643 | 0.55 | 0.55 | 16.482 |
| full M1 | 180,436 | 0.90 | 0.45 | 2.190 |

These one-seed smoke results are diagnostic only. The hidden-cue score is not a
fair test of recurrence for the modular agent yet because its state is reset
per forward call; the GRU control remains the proper recurrent reference.
The combined Engram/JEPA/Loop latency also needs profiling before interpreting
it as a stable systems result.

| Engram + JEPA + Loop | 0.533 | 0.467 | 0.189 | 3.098 |

The short 30-episode runs are noisy and the hidden score is not a valid memory
measure for the stateless modular agent. They are retained to expose variance;
the recurrent GRU control and a stateful Loop Transformer need to be evaluated
in the next controlled run.
